## 1. 架构定位

```
开发者A ──IDE + MCP Server(stdio)──┐
开发者B ──IDE + MCP Server(stdio)──┼── HTTP REST ──→ Search Service ──→ [开发] SQLite/FAISS/NetworkX
开发者C ──IDE + MCP Server(stdio)──┘                  (FastAPI, 团队共享)  [生产] ES/Milvus/Neo4j
```

- **MCP Server**：每IDE一个进程，stdio 通信，负责协议适配 + Prompt 组装
- **Search Service**：独立微服务，团队共享，承载混合检索 + 索引管理
- **后端双模式**：`BACKEND_MODE=lightweight`（默认，免外部服务）或 `production`（ES/Milvus/Neo4j）
- MCP Server 通过 `RemoteSearchEngine` + `RemoteKnowledgeBase` 调用 Search Service

### 3.2 GET /api/v1/entities/{name}

精确查询实体（术语或API）的完整结构化定义。

**函数签名：**
```python
async def get_entity(
    name: str,                              # path
    entity_type: str | None = None,         # query, 可选 "term" | "api"
    version_requirement: str | None = None, # query, 可选 ">=2.1.0"
) -> EntityDetailResponse
```

**Response:** 返回 `EntityDetailResponse` 结构（与 MCP 层一致），但**不含 `found`/`message` 字段**。检索不到时返回默认空 `EntityDefinition`。

### 3.3 GET /api/v1/specs

根据模块、文件路径获取适用的规范契约。

**函数签名：**
```python
async def get_specs(
    module: str | None = None,
    file_path: str | None = None,
    dependency_constraints: str | None = None,  # JSON string
) -> SpecResponse
```

**Response:** `SpecResponse` 结构，含 `specs: list[SpecItem]` 和 `conflict_warnings: list[str]`。

上报知识采纳/拒绝反馈，记录 feedback_id。权重调整逻辑后续实现。

|------|------|------|

逐一检查 ES / Milvus / Neo4j 连接状态。轻量模式下后端未部署时返回 `false`。

```json
  "milvus": true,
  "neo4j": true
}
```
- `status`: `ok`（全部可用） | `degraded`（部分可用） | `down`（全部不可用）

## 4. 混合检索引擎（核心）

### 4.1 工厂模式

`engine/factory.py` 根据 `BACKEND_MODE` 环境变量创建对应后端实例，创建时传入 `ServiceConfig` 中对应的路径/连接参数：

```python
BACKEND_MODE=lightweight → LiteBM25Searcher(sqlite_db_path)
                           LiteVectorSearcher(faiss_index_dir)
                           LiteGraphSearcher(graph_storage_path)
BACKEND_MODE=production  → BM25Searcher()
                           VectorSearcher()
                           GraphSearcher()
```

```python
from .factory import create_bm25_searcher, create_vector_searcher, create_graph_searcher

class HybridSearcher:
    def __init__(self):
        self.bm25 = create_bm25_searcher()
        self.vector = create_vector_searcher()
        self.graph = create_graph_searcher()
```

所有后端实现均满足 `backends/protocols.py` 中定义的 `SearcherProtocol` 接口（`available: bool` 属性 + `async search(query, context, knowledge_types, top_k) -> list[KnowledgeItem]` 方法）。

### 4.2 混合检索流水线

**`HybridSearcher.search()` 函数签名：**
```python
async def search(
    query: str,
    context: SearchContext | None = None,
    knowledge_types: list[KnowledgeType] | None = None,
    top_k: int = 5,
    min_score: float = 0.7,
) -> tuple[list[KnowledgeItem], Diagnostics]
```

**流水线：**

```
  query + context
       │
       ├─→ BM25 (SQLite/ES)       ─→ top_k * candidate_multiplier(默认3) 候选
       ├─→ 向量 (FAISS/Milvus)    ─→ top_k * candidate_multiplier 候选
       └─→ 图遍历 (NetworkX/Neo4j)─→ 关联实体文档
              │
              ↓ 三路并行检索（asyncio.gather，各路由 _safe_search 保护，超时 search_timeout_ms）
         合并 + 去重（按 ID，保留最高分）
              │
              ↓
         重排序（类型boost + 角色boost + 关键词命中加成）
              │
              ↓
         Top-K 裁剪（min_score 过滤 + top_k 截断）
              │
              ↓
         {items, diagnostics}
```

**`_safe_search`**：每个后端调用由 `asyncio.wait_for()` 包裹，超时阈值 `service_config.search_timeout_ms`（默认 300ms）。超时或异常时不中断整体检索，仅记录警告到 `Diagnostics.warnings`。

### 4.3 轻量后端（`backends/lite/`）

| 能力 | 组件 | 关键实现 |
|------|------|----------|
| 全文检索 | SQLite FTS5 | `bm25()` 排序，FTS5 OR 匹配（多词召回），结果集内相对归一化（最高→1.0，最低→0.1） |
| 向量检索 | FAISS | `IndexFlatIP` 内积相似度，文件持久化（vectors.index + id_map.json） |
| 图遍历 | NetworkX | 内存有向图，节点内容子串匹配，JSON 文件持久化；`flush()` 批量写入（避免逐条 IO） |
| Embedding | sentence-transformers / 零向量 | 默认加载 `BAAI/bge-small-zh`，`encode(normalize_embeddings=True)` 输出归一化向量；模型不可用时返回 `[0.0]*dim` 占位；`dim` 属性动态读取 `model.get_sentence_embedding_dimension()`，兜底 768 |

**轻量后端的优雅降级**：所有本地组件必定可达（`available = True`），无数据时返回空结果。异常通过 `logger.exception` 记录。

**大规模数据优化（v1.4）**：图模块 `add_entity/add_relation` 不再自动保存，改为 orchestrator 批量加载后调用 `graph.flush()` 一次性持久化（避免 2 万+节点时 O(n²) IO）。BM25 FTS5 多词查询从默认 AND 改为 OR（`"JSONArray OR parse"`），配合结果集内线性相对归一化，避免单结果得分过低被 `min_score` 过滤。

### 4.4 生产后端（`backends/production/`）

BM25 → Elasticsearch / 向量 → Milvus / 图遍历 → Neo4j。模块由原 `engine/` 平铺位置移入，内容不变，仅 `import` 路径更新为 `....models`。

### 4.5 重排序器 (`engine/ranker.py`)

本节对应 `doc/1.requirement.md` 第6章「技术选型推荐」中的「重排序」选型：当前采用 Heuristic 加权，后续可替换为 Cross-BERT / 本地 CrossEncoder 模型。

**`rerank(items, query, query_context_module=None) -> tuple[list[KnowledgeItem], list[LayeredRecommendation]]`**（v1.3 起返回 tuple）

**类型 boost：**

| 类型 | boost |
|------|-------|
| api | 1.00 |
| best_practice / spec | 0.95 |
| document / defect_history | 0.90 |
| security_rule | 0.85 |
| term | 0.80 |
| test_template | 0.75 |

**SDK 角色 boost（v1.4 差距扩大到 3.3x，无条件生效）：**

| 角色 | boost |
|------|-------|
| entry_point | 1.00 |
| public_api | 0.80 |
| internal | 0.55 |

**层级 boost（v1.4 无条件生效，high vs low 差 2.7x）：**

| 层级 | boost | 触发条件 |
|------|-------|----------|
| high | 1.50 | 无条件（v1.4 移除语义阈值门控） |
| mid | 1.00 | 默认 |
| low | 0.55 | 有 `suggested_alternative` 时；无替代时 0.78 |

**入口 gateway 加成（v1.4 新增）**：`entry_point` + 有 `return_type` 且非基本类型 → ×1.15。

**关键词命中加成**：每个命中关键词 ×1.03（v1.4 改为乘法缩放，取代固定加法）。

**公式**：`final_score = item.score * type_boost * role_boost * layer_boost * keyword_factor * (gateway_boost)`

**归一化**：最高分映射到 1.0，其余等比缩放。

推广期替换为 Cross-BERT / 本地 CrossEncoder 模型。

MCP Server 侧仅消费 Search Service 返回的 Top-K 结果，不感知重排序实现细节；MCP 调用链中的对应位置见 `doc/3.mcp_design.md` 第7章「工具间协作流程」。

## 6. 数据预处理管道

`pipeline/` 目录提供数据预处理骨架，企业数据到位后调用 `orchestrator.run(data_dir)` 即可灌入后端：

```
loader.load("docs/*.md")           # 加载文档
  → chunker.chunk_text(text)       # 分块（3K-5K tokens，重叠窗口）
    → embedding.embed(chunks)      # 向量化（bge-small-zh / 零向量降级）
      → bm25.index_documents()     # 写入 SQLite FTS5（或 ES）
      → vector.index_vectors()     # 写入 FAISS（或 Milvus）
      → graph.add_entity/relation()# 写入 NetworkX（或 Neo4j）
```

**分块策略**：按空行+标题边界切段落，合并至 3K-10K 字符（~1500-5000 tokens），块间重叠 ~300 tokens。

**运行方式**：
```bash
# 摄入指定目录下的 Markdown / Python / Go 文件
python -m search_service.pipeline.orchestrator doc/

# 或从代码调用
from search_service.pipeline.orchestrator import run
stats = run("doc/", patterns=["**/*.md"])
# → {"files": 7, "chunks": 9, "indexed_bm25": 9, "indexed_vector": 9, "graph_nodes": 9}
```

## 7. 启动方式

```bash
# 安装依赖
pip install -r search_service/requirements.txt

# 默认 lightweight 模式（SQLite + FAISS + NetworkX，免外部服务）
uvicorn search_service.main:app --host 0.0.0.0 --port 8080

# 生产模式（需先 docker compose up 启动 ES/Milvus/Neo4j）
BACKEND_MODE=production uvicorn search_service.main:app --host 0.0.0.0 --port 8080

# 或直接运行
python -m search_service.main
```

MCP Server 侧通过 `SEARCH_SERVICE_URL` 环境变量指向该服务：
```bash
export SEARCH_SERVICE_URL=http://localhost:8080
python -m inner_sdk_search_mcp.server
# 未设置时自动使用 Mock 实现
```

## 8. 数据模型

`search_service/models/schemas.py` 与 `mcp/models/schemas.py` 结构完全一致，包含：

- `SearchRequest` / `SearchResponse` — 混合检索
- `EntityDetailResponse` — 实体查询
- `SpecResponse` — 规范契约
- `PinnedKnowledge` — 上下文推荐
- `FeedbackRequest` / `FeedbackResponse` — 反馈上报
- `HealthStatus` — 健康检查（Search Service 特有）

两边的模型可考虑后续抽取为共享 package（pip install 或 git submodule）。
