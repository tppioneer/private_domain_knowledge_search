## 1. 模块定位

数据预处理管道负责将企业私域数据（设计文档、SDK 源码）转化为可检索的索引，供 Search Service 的混合检索引擎消费。

```
企业数据
  ├── Markdown / Python / Go 文本 ──→ loader → classifier → chunker ─┐
  └── Java SDK 源码                  ──→ code_parser ─────────────────┤
                                                                   ↓
                                                             orchestrator
                                                                   ↓
                                                          BM25 + FAISS + Graph
```

---

## 2. 项目结构

```
search_service/pipeline/
├── __init__.py
├── loader.py          # 文件加载器（glob 模式匹配）
├── classifier.py      # 文档类型分类器（规则匹配）
├── chunker.py         # 文档分块器（段落分块 + API 章节特殊处理）
├── code_parser.py     # Java SDK AST 解析器（pom.xml + javalang）
└── orchestrator.py    # 编排入口：加载 → 分类 → 分块 → Java解析 → 索引
```

## 3. 核心组件

### 3.1 loader.py —— 文件加载器

**职责**：按 glob 模式从目录加载文件内容。

**函数**：`load_files(root_dir: str, patterns: list[str] | None = None) -> list[dict]`

**默认模式**：`["**/*.md", "**/*.py", "**/*.go"]`。文件类型由 `classifier.py` 推断，loader 只负责读取文本。

**实现要点**：
- 使用 `pathlib.Path.glob()` 递归匹配
- UTF-8 编码读取，失败则跳过
- 返回相对路径和原始文本内容，不做任何分块

### 3.2 chunker.py —— 文档分块器

**职责**：将文本切分为统一 chunk；普通文档按段落 + 重叠窗口处理，Markdown API 文档按 API 章节/子标题拆成独立 API chunk。

**入口函数**：
```python
def chunk_text(
    text: str,
    source_path: str = "",
    title: str = "",
    chunk_type: str = "document",
    module: str = "",
) -> list[dict]
```

**内部辅助函数**：
| 函数 | 入参 | 出参 | 说明 |
|------|------|------|------|
| `_estimate_tokens(text)` | `text: str` | `int` | 按 `len(text) / 2.0` 粗略估算 token 数 |
| `_split_paragraphs(text)` | `text: str` | `list[str]` | 按空行切段，并将小段合并到至少 `_MIN_CHUNK_SIZE=3000` 字符 |
| `_find_api_section_start(text)` | `text: str` | `int \| None` | 查找 `## API` / `### API` / `REST API` / `接口` 等章节起点 |
| `_split_api_entries(api_text)` | `api_text: str` | `list[dict]` | 按 `###` / `####` 子标题切分 API 条目，并提取 REST 方法与路径 |
| `_build_chunk_dict(...)` | `content, source_path, title, chunk_type, module, start_idx, extra_meta` | `dict` | 构造统一 chunk 字典 |
| `_make_chunk_id(source_path, index)` | `str, int` | `str` | `md5(f"{source_path}:{index}")[:12]` |

**分块策略**：
1. 如果检测到 API 章节：
   - API 章节前的内容按普通文档分块，`type=document`
   - API 章节内按 `###` / `####` 子标题切分，每个 API 条目生成一个 `type=api` 的 chunk
   - 若正文中出现 `GET|POST|PUT|DELETE|PATCH|HEAD|OPTIONS /path`，写入 `api_type=rest`、`http_method`、`url_path`
2. 如果未检测到 API 章节：
   - 按空行切分段落
   - 合并至 `_MAX_CHUNK_SIZE=10000` 字符以内
   - 超限时写出当前 chunk，并用 `_OVERLAP_SIZE=600` 字符作为重叠窗口
3. 输出 chunk 可直接传给 BM25 / Vector / Graph 三类索引器。

**普通文档 chunk 结构**：
```python
{
    "id": "0932a6a4c60f",
    "type": "document",
    "content": "# 私域知识...",
    "title": "requirement",
    "module": "doc",
    "source_path": "doc/requirement.md",
    "tokens": 1800,
    "meta_json": "{...}"
}
```

**`meta_json` 基础结构**：
```json
{
  "knowledge_source": "doc",
  "source": "doc/requirement.md",
  "type": "document"
}
```

**REST API chunk 的额外 `meta_json` 字段**：
```json
{
  "api_type": "rest",
  "http_method": "POST",
  "url_path": "/api/v1/search"
}
```

**`knowledge_source` 字段**：
| 值 | 含义 | 写入方 |
|----|------|--------|
| `"doc"` | Markdown / 设计文档 / API 文档 | `chunker.py` |
| `"sdk_code"` | Java SDK 源码解析结果 | `code_parser.py` |

### 3.3 code_parser.py —— Java AST 解析器

**职责**：解析 Java SDK 源码仓库，提取 Maven 坐标、public 方法、public 构造函数、Javadoc、调用链与 SDK 角色标记，输出统一 chunk。

**公开入口函数**：
| 函数 | 入参 | 出参 | 说明 |
|------|------|------|------|
| `extract_pom_info(pom_path)` | `pom_path: str` | `dict \| None` | 解析单个 `pom.xml`，返回 `group_id/artifact_id/version` |
| `discover_pom_modules(repo_dir)` | `repo_dir: str` | `list[dict]` | 递归扫描所有 `pom.xml`，按深度排序，并应用版本覆盖/继承 |
| `parse_java_file(filepath, sdk_meta)` | `filepath: str`, `sdk_meta: dict` | `list[dict]` | 解析单个 `.java` 文件，输出方法/构造函数 chunk |
| `parse_java_repo(repo_dir)` | `repo_dir: str` | `list[dict]` | 发现 Maven 模块，过滤 test 目录，汇总所有 Java chunk |

**主要内部函数**：
| 函数 | 入参 | 出参 | 说明 |
|------|------|------|------|
| `_load_version_overrides(repo_dir)` | `str` | `dict[str, str]` | 读取 `.sdk-versions.json` |
| `_resolve_version(artifact_id, pom_version, overrides)` | `str, str, dict` | `str` | `.sdk-versions.json` → pom 字面量 → 空字符串 |
| `_detect_class_role(package_name, class_path, method_nodes)` | `str, str, list[tuple]` | `str` | 返回 `entry_point/public_api/internal` |
| `_extract_javadocs(source)` | `str` | `dict[int, str]` | 提取 public 方法起始行号到 Javadoc 文本的映射 |
| `_method_to_chunk(...)` | AST 方法节点及 SDK 元数据 | `dict` | 生成方法 chunk |
| `_constructor_to_chunk(...)` | AST 构造函数节点及 SDK 元数据 | `dict` | 生成构造函数 chunk |
| `_extract_calls(method_node)` | AST 方法节点 | `list[str]` | 提取方法体内 `MethodInvocation.member` |

**处理流水线**：

```
repo_dir/
  ├── pom.xml              ──→  discover_pom_modules()    → Maven 模块列表
  ├── .sdk-versions.json   ──→  _load_version_overrides() → 版本覆盖表
  └── **/*.java            ──→  parse_java_file()         → 方法/构造函数 chunk
                                     │
                                     ├── 跳过路径包含 /test/ 的文件
                                     ├── javalang AST 解析
                                     ├── 仅 public 方法 + public 构造函数
                                     ├── _extract_javadocs() 关联注释
                                     └── _extract_calls() 提取调用链
```

**方法 chunk 示例**（全限定 import + 简短调用签名 + 返回类型）：
```json
{
  "id": "15d19109473f",
  "type": "api",
  "content": "import com.example.sdk.PointsClient;\nPointsClient.deduct(String bizId, String uid, int points) → String\n\n积分扣减\n@param bizId 业务幂等键",
  "title": "PointsClient.deduct",
  "module": "points-sdk",
  "source_path": "src/main/java/com/example/sdk/PointsClient.java",
  "meta_json": "{\"knowledge_source\": \"sdk_code\", \"sdk\": \"points-sdk\", \"version\": \"2.3.0\", \"class_name\": \"com.example.sdk.PointsClient\", \"method\": \"deduct\", \"return_type\": \"String\", \"calls\": [\"validateParams\"], \"role\": \"entry_point\"}"
}
```

**构造函数 chunk 差异**：
```json
{
  "content": "import com.example.sdk.PointsException;\nnew PointsException(String message)",
  "title": "PointsException.constructor",
  "meta_json": "{\"method\": \"PointsException\", \"return_type\": \"PointsException\"}"
}
```

**关键字段**：

| 字段 | 来源 | 说明 |
|------|------|------|
| `id` | `_make_id(f"{sdk_id}:{fqn}")` 或构造函数加 `:constructor` | 12 位 MD5 |
| `type` | 固定值 | `api` |
| `content` | `_method_to_chunk()` / `_constructor_to_chunk()` | `import ...;` + 调用签名 + Javadoc |
| `title` | 类名 + 方法名 | 如 `PointsClient.deduct` / `PointsException.constructor` |
| `module` | `sdk_id` | Maven `artifact_id` |
| `source_path` | `filepath` | `parse_java_file()` 入参，可能为相对或绝对路径 |
| `meta_json.knowledge_source` | 固定值 | `sdk_code` |
| `meta_json.sdk` | `artifact_id` | SDK 标识 |
| `meta_json.version` | 版本解析链（见 3.3.1） | 真实发布版本；无法解析时为空字符串 |
| `meta_json.class_name` | `package + class_path` | 完整 import 路径 |
| `meta_json.method` | AST 节点 | 方法名；构造函数为类名 |
| `meta_json.return_type` | AST 返回类型 | 方法返回类型；构造函数为类名 |
| `meta_json.calls` | `_extract_calls()` | 仅方法 chunk 有该字段；构造函数无 `calls` |
| `meta_json.role` | `_detect_class_role()` | `entry_point` / `public_api` / `internal` |

#### 3.3.0 SDK 角色推断（v1.3，v1.5 增强）

`code_parser.py` 的 `_detect_class_role()` 根据包路径 + 类名模式 + 方法特征自动标注，共 6 条规则按优先级判定：

**判定规则：**

| # | 条件 | 结果 | 示例 |
|---|------|------|------|
| 1 | 叶子包 ∈ {dao, config, impl, internal, model, dto, vo} | `internal` | `LocalFileStorageDao.upload()` |
| 2 | 所有方法为 getter/setter（含 isXxx、toString、hashCode、equals） | `internal` | 纯 POJO/DTO |
| 3a | 方法返回自身类型 + 含 `build()` 方法（Builder 模式） | `entry_point` | `FileStorageConfig.Builder.build()` |
| 3b | 类名后缀 ∈ {Factory, Manager, Client, Bootstrap, Starter, Builder} + 在根包 + 有非 getter 方法 | `entry_point` | `PointsFactory.getClient()` |
| 3c | 含静态工厂方法（static + 返回非基本类型）+ 在根包或 public 子包 | `entry_point` | `FileServiceManager.getTenantService()` |
| 3d | 类名带入口后缀 + 在 service/api/client/facade 子包 | `entry_point` | Spring Bean 风格入口 |
| 4 | 叶子包 ∈ {service, api, client, facade} | `public_api` | `FileService.uploadFile()` |
| 5 | 根包（无子包或叶子包为顶级包） | `public_api` | 接口/抽象类/枚举 |
| 6 | 叶子包 = util | `public_api` | 工具类属于公开能力 |
| — | 以上均不匹配（兜底） | `internal` | — |

**辅助检测函数：**
- `_all_getters_setters()` — 判断方法列表是否全为 getter/setter/toString/hashCode/equals
- `_has_static_factory()` — 判断是否含 static + 返回非基本类型的方法
- `_has_self_returning_methods()` — 判断是否有方法返回自身类型（Builder 模式特征）
- `_has_build_method()` — 判断是否含 `build()` 方法（Builder 模式标志）

**子包分类**：从 `package_name`（如 `com.company.file.service`）提取叶子包（`service`），与预定义子包集合匹配。解决了 v1.3 中仅用 `class_path`（类名）导致子包检测失效的 bug。

**ranker.py** 叠加角色加成（entry_point 1.0 > public_api 0.92 > internal 0.80），确保 Manager 方法排名高于 DAO 实现。

**实测数据**：com-ext-file（8 类）：FileServiceManager=entry_point，3 个 Service=public_api，4 个 DAO/Config=internal。fastjson（207 类，1552 方法）：55 entry_point / 129 public_api / 23 internal。

#### 3.3.0.1 方法层级检测（v1.7）

`_detect_method_layer()` 根据类名 + 角色 + 参数复杂度推断方法层级：`high` | `mid` | `low`。

**判定规则**（按优先级）：

| # | 条件 | 结果 |
|---|------|------|
| 1 | 类名含 `impl` / `internal` | `low` |
| 2 | `class_role == entry_point` → **无条件 `high`**（v1.7 修复：不再因 Config 参数误标 low） | `high` |
| 3 | 类名含 Manager/Facade/Gateway/Helper 等后缀 + 参数 ≤2 + public 角色 | `high` |
| 4 | 参数含 Context/Request/Response/Session/Config 等复杂对象 | `low` |
| 5 | 叶子包 ∈ {dao, config, impl, internal, model, dto, vo} | `low` |
| 6 | 叶子包 ∈ {service, api, client, facade} | `mid` |
| — | 兜底 | `mid` |

**ranker 联动**：`high` 层 ×1.50，`low` 层 ×0.55（有高层替代时）。

#### 3.3.0.2 构造入口检测（v1.8）

`_detect_construction_pattern()` 检测 SDK 实例的构造方式，识别四种模式：

| 模式 | 判定条件 | 示例 |
|------|----------|------|
| `builder` | `static` + 方法名 `newBuilder`/`builder` | `EcsClient.newBuilder()` |
| `static_factory` | `static` + 返回非 void/基本类型 | `FileServiceManager.getSystemService()` |
| `singleton` | `static` + 方法名 `getInstance`/`getDefault`/`getSingleton`/`instance` | `Config.getInstance()` |
| `constructor` | `ConstructorDeclaration` 节点 | `new FileServiceManager(config)` |

写入 chunk meta 的 `construction_pattern` 字段，下游消费：

| 消费者 | 用途 |
|--------|------|
| ranker | `_CONSTRUCTION_BOOST = 1.25`，构造方法排到入口类最前面 |
| assembler | 精确构造指引文本（"`FileServiceManager` 通过静态工厂构造：`getSystemService(...)`） |
| search_private_knowledge | `construction_guide` 字段返回构造指引明文 |

#### 3.3.1 版本解析链

解决 pom.xml 中占位符版本（SNAPSHOT / `${revision}` / 空）无法作为真实版本的问题。

```
.sdk-versions.json（权威覆盖）
     ↓ 未命中
pom.xml 字面量（非占位符时采用）
     ↓ 占位符
空字符串（兜底，检索时不按版本过滤）
```

**`.sdk-versions.json` 格式**：
```json
{
  "points-sdk": "2.3.0",
  "snapshot-lib": "2.5.0"
}
```

**占位符检测**：正则匹配 `${.*}` / `.*-SNAPSHOT` / 空字符串，命中后记录 INFO 日志并降级为空。

**兜底行为**：版本为空字符串时，BM25 检索不施加版本过滤——任何匹配的方法签名都返回。

#### 3.3.2 Javadoc 提取

在 javalang 解析前用正则预提取 `/** ... */` 注释块，按紧邻 public 方法的行号关联。清洗后的文本附加到 chunk.content 中，使方法签名 + 注释可同时被全文检索命中。

### 3.4 orchestrator.py —— 编排器

**职责**：串联加载、分类、分块、Java AST 解析、Embedding、BM25/FAISS/Graph 索引写入；当前直接实例化 Lite 后端，不走 factory。

**入口函数**：
```python
def run(
    data_dir: str,
    patterns: list[str] | None = None,
) -> dict
```

**函数入参**：
| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `data_dir` | `str` | 必填 | 数据根目录；同时作为文档加载根目录和 Java 仓库根目录 |
| `patterns` | `list[str] \| None` | `None` | 传给 `load_files()`；为空时加载 `**/*.md`、`**/*.py`、`**/*.go` |

**流水线**：

```
1. load_files(data_dir, patterns)                      → [{path, filename, content}]
2. classify_document(f["path"], f["content"][:800])   → KnowledgeType
3. 从 f["path"] 第一段推断 module；filename stem 作为 title
4. chunk_text(content, source_path, title, chunk_type, module)
5. parse_java_repo(data_dir)                           → Java 方法/构造函数 chunk
6. LiteBM25Searcher(service_config.sqlite_db_path).index_documents(all_chunks)
7. get_embedding_model().embed([chunk.content])
8. LiteVectorSearcher(service_config.faiss_index_dir).index_vectors(ids, vectors, metas)
9. LiteGraphSearcher(service_config.graph_storage_path).add_entity(...)
10. 同 source_path 的相邻 chunk 建立 RELATED_TO 边
11. graph.flush() 一次性持久化
```

**向量索引 meta 结构**：
```python
metas = [{
    "type": c["type"],
    "content": c["content"],
    "title": c["title"],
    "module": c["module"],
    "source_path": c["source_path"],
} for c in all_chunks]
```

**Graph 节点 meta 结构**：
```python
graph.add_entity(c["id"], c["type"], c["content"], {
    "title": c["title"],
    "module": c["module"],
    "source_path": c["source_path"],
})
```

**输出统计**：
```json
{
  "doc_files": 7,
  "doc_chunks": 9,
  "java_chunks": 4,
  "total_chunks": 13,
  "indexed_bm25": 13,
  "indexed_vector": 13,
  "graph_nodes": 13
}
```

**注意事项**：
- `doc_chunks = len(all_chunks) - java_chunk_count`，包含文档分块后的所有非 Java AST chunk。
- BM25 写入的是完整 chunk，包括 `meta_json`。
- FAISS 和 Graph 当前只写入轻量 meta，不包含完整 `meta_json`。
- 每次运行是追加/覆盖式行为取决于具体后端实现；当前不支持 source_path 级增量更新。

**运行方式**：
```bash
# 摄入当前项目文档 + Java SDK 源码
python -m search_service.pipeline.orchestrator .

# 指定数据目录和文件模式
python -m search_service.pipeline.orchestrator /path/to/data

# 编程调用
```

## 4. 数据流与接口约定

### 4.1 文件加载输出

`loader.load_files()` 输出：
```python
{
    "path": str,      # 相对 root_dir 的路径
    "filename": str,  # 文件名，含扩展名
    "content": str,   # UTF-8 文本内容
}
```

### 4.2 分类器接口

`classifier.classify_document(filepath, content_preview="") -> KnowledgeType`

优先级与当前代码一致：
```text
扩展名(.java/.py/.go) > 目录路径 > 文件名 > 内容关键词 > document
```

代码文件扩展名会直接归类为 `KnowledgeType.API`；文档内容只读取前 800 字符作为 `content_preview`。

### 4.3 统一 chunk 字典

所有组件通过统一 chunk 字典传递数据：

```python
chunk = {
    "id": str,
    "type": str,
    "content": str,
    "title": str,
    "module": str,
    "source_path": str,
    "meta_json": str,
    "tokens": int,  # 仅 chunker.py 生成的文档 chunk 包含；code_parser.py 生成的 SDK chunk 不包含
}
```

| 字段 | 必填 | 写入方 | 说明 |
|------|------|--------|------|
| `id` | 是 | `chunker.py` / `code_parser.py` | 12 位 MD5 |
| `type` | 是 | `classifier.py` / `code_parser.py` | 文档 chunk 使用分类结果；SDK chunk 固定为 `api` |
| `content` | 是 | `chunker.py` / `code_parser.py` | 可检索文本；SDK chunk 为 import + 调用签名 + Javadoc |
| `title` | 是 | `orchestrator.py` / `code_parser.py` | 文件 stem / API 标题 / 类名.方法名 |
| `module` | 是 | `orchestrator.py` / `code_parser.py` | 路径第一段 / Maven `artifact_id` |
| `source_path` | 是 | `loader.py` / `code_parser.py` | 文档相对路径；Java 文件路径来自 `Path.rglob()` |
| `meta_json` | 是 | `chunker.py` / `code_parser.py` | JSON 字符串，存结构化元数据 |
| `tokens` | 否 | `chunker.py` | 文档 chunk 的粗略 token 数 |

### 4.4 `meta_json` 结构

文档 chunk：
```json
{
  "knowledge_source": "doc",
  "source": "doc/5.pipeline_design.md",
  "type": "document"
}
```

REST API 文档 chunk 会额外包含：
```json
{
  "api_type": "rest",
  "http_method": "GET",
  "url_path": "/api/v1/health"
}
```

Java SDK chunk：
```json
{
  "knowledge_source": "sdk_code",
  "sdk": "points-sdk",
  "version": "2.3.0",
  "class_name": "com.example.sdk.PointsClient",
  "method": "deduct",
  "return_type": "String",
  "calls": ["validateParams"],
  "role": "entry_point"
}
```

### 4.5 索引器接口约定

| 组件 | 调用方式 | 输入 | 输出 | 备注 |
|------|----------|------|------|------|
| BM25 | `LiteBM25Searcher.index_documents(all_chunks)` | `list[dict]` | `int` | 写入 `doc_id/type/content/title/module/meta_json` 到 SQLite FTS5 |
| Vector | `LiteVectorSearcher.index_vectors(ids, vectors, metas)` | `list[str]`, `list[list[float]]`, `list[dict]` | `int` | 写入 FAISS `vectors.index` 与 `id_map.json` |
| Graph | `LiteGraphSearcher.add_entity(id, type, content, meta)` | 单个 chunk 拆出的字段 | `None` | 写入 NetworkX 节点，最后调用 `flush()` 持久化 |
| Graph Relation | `LiteGraphSearcher.add_relation(source, target, "RELATED_TO")` | 相邻 chunk id | `None` | 同一 `source_path` 下相邻 chunk 建边 |

### 4.6 三类索引的数据差异

| 后端 | 保留字段 | 是否保留完整 `meta_json` |
|------|----------|--------------------------|
| SQLite FTS5 | `doc_id/type/content/title/module/meta_json` | 是 |
| FAISS id_map | `doc_id/type/content/title/module/source_path` | 否 |
| NetworkX node.meta | `title/module/source_path` | 否 |

因此，当前需要依赖 SDK 详细元数据（如 `class_name`、`return_type`、`role`）的检索结果，主要由 BM25 路径返回时最完整；FAISS/Graph 路径当前只保留轻量展示元数据。

## 6. 扩展点

### 6.1 新增文件类型支持

在 `loader.py` 的 `patterns` 参数中添加 glob 模式，在 `classifier.py` 的 `_EXT_PATTERNS` / `_DIR_PATTERNS` / `_FILENAME_PATTERNS` / `_CONTENT_PATTERNS` 中补充分类型规则。

### 6.2 新增语言 AST 解析

参照 `code_parser.py` 的模式：
1. 读取构建文件提取包名/版本（Python 读 `setup.py` / `pyproject.toml`）
2. 用对应语言的 AST 库解析源码（Python 用 `ast` 标准库）
3. 输出统一 chunk 格式
4. 在 `orchestrator.py` 中调用

### 6.3 对接生产后端

将 `BACKEND_MODE` 设为 `production`，pipeline 通过 factory 创建的将是 ES/Milvus/Neo4j 实例。但 `orchestrator.py` 当前直接实例化 Lite* 类——这是已知限制（见 review LOW 优先级），生产模式下需调整。

### 6.4 增量更新

当前 orchestrator 每次全量覆写。增量更新需：
1. 追踪 source_path → chunk_id 的映射
2. 对比文件修改时间，仅重处理变更文件
3. 删除已移除文件对应的旧 chunk

## 7. 已知问题与修复记录

### 7.1 大规模 Java SDK 导入性能

**问题**：fastjson（3119 文件）导入时图构建卡死。

**根因**：`LiteGraphSearcher.add_entity/add_relation` 每次调用 `_save()` 写全量 JSON，O(n²) IO。20441 节点每次都序列化几十 MB。

**修复**（v1.4）：移除 add 方法的自动 `_save()`，新增 `flush()` 方法。orchestrator 批量加载后一次性调用。

### 7.2 FTS5 多词查询命中率极低

**问题**：搜索 `"JSONArray parse"` 只命中 1 条，归一化得分 0.092 < min_score=0.7，全部被过滤。

**根因**：FTS5 MATCH 多词默认 AND 语义；sigmoid 公式 `1/(1+e⁻ˣ)` 对低分零值映射为 0.5，再经 ranker 加成仍低于阈值。

**修复**（v1.4）：FTS5 查询改为 OR（`"JSONArray OR parse"`）；分数归一化改为结果集内线性相对映射（最高→1.0，最低→0.1）。

### 7.3 FAISS 维度不匹配 AssertionError

**问题**：`assert d == self.d`，pipeline 在 FAISS `add()` 时报错。

**根因**：`bge-small-zh` 实际输出 512 维，但 `embedding.dim` 和 `vector._dim` 硬编码为 768。模型可用时维度不匹配。

**修复**（v1.4）：`embedding.dim` 改为从加载的模型动态读取 `get_sentence_embedding_dimension()`；`vector._dim` 改为 property 走 embedding 单例。`index_vectors` 增加维度不匹配时自动重建索引逻辑。

### 7.4 test 目录代码污染

**问题**：`src/test/java` 下单测代码被当作 SDK API 索引，fastjson test 占总量 94%。

**修复**（v1.4）：`parse_java_repo` 中对 `.java` 文件路径包含 `/test/` 的跳过。

### 7.5 Embedding 模型首次请求阻塞

**问题**：embedding 模型采用延迟加载，首次请求触发 `SentenceTransformer` 初始化和权重下载，阻塞数分钟。

**修复**（v1.4）：`main.py` 的 FastAPI `lifespan` 启动阶段调用 `get_embedding_model()` 预加载。uvicorn 启动时即完成模型加载，首次请求不再阻塞。
